What IAM means

IAM is the framework of policies and technologies that ensures the right users get the right access to the right resources at the right time. Core functions are identifying users, authenticating them, authorizing actions, and tracking access history.

Identity

A digital representation of a user, service, device, or workload.

Authentication

Proving who you are, for example password plus MFA.

Authorization

Deciding what you can do after login.

Why IAM is central

🔐

Primary perimeter

Modern guidance treats identity as the main security boundary instead of trusting the internal network.

👤

Stops account misuse

Least privilege and strong verification reduce lateral movement when a standard account is compromised.

📋

Supports audit

Provisioning, role assignment, and login records help with compliance and investigations.

Authentication vs authorization

Authentication

  • Checks identity.
  • Examples: password, passkey, OTP, smart card, biometrics.
  • Question answered: “Are you really Alice?”

Authorization

  • Checks permissions after login.
  • Examples: read-only, approver, admin, database owner.
  • Question answered: “What can Alice do now?”

Example: a developer signs into the company portal with MFA, then receives permission to open Jira and GitHub, but not payroll or production root access.

Common IAM building blocks

Directory

Stores users, groups, and attributes such as department and manager.

SSO and federation

One login across many apps using standards such as SAML and OpenID Connect.

MFA

Adds a second factor to make stolen passwords less useful.

RBAC / ABAC

Assigns access by roles or by attributes and context.

IGA

Governance workflows for joiner mover leaver, certifications, and policy checks.

PAM

Secures admin credentials with vaulting, rotation, JIT elevation, and session recording.

Access control models

RBAC

Access depends on job role. Easy to manage in enterprises, for example “L1 Support” or “HR Manager”.

ABAC

Access depends on attributes like department, location, device trust, or data sensitivity.

JIT / JEA

Privilege is granted only for a short time and only for a defined task.

Teaching example: RBAC lets every finance analyst view financial reports, ABAC can further restrict access to only analysts in India using a managed laptop during business hours.

Least privilege in practice

Rule

Give only the minimum access needed for the task, nothing more, and remove it when the task ends.

0
core principle to repeat throughout the course

Example

A database engineer gets temporary elevation for a production change window, session recording is enabled, and the rights expire automatically after the ticket closes.

Good: separate admin and normal user accounts.

Bad: shared “superadmin” password known to the whole team.

Risk: standing privilege becomes attacker privilege after compromise.

Joiner mover leaver lifecycle

Joiner

Create identity, assign starter roles, issue MFA, and provision baseline applications.

Mover

When department or project changes, remove old access and grant only the new entitlements.

Leaver

Disable accounts fast, rotate secrets, revoke sessions, and archive logs for audit.

Review

Managers and application owners certify that access is still needed.

Core enterprise controls

Single sign-on

Improves user experience and centralizes control, but federation trust must be configured carefully.

Phishing-resistant MFA

Use stronger verification methods to reduce the value of stolen passwords and OTP fatigue attacks.

Conditional access

Use device trust, geolocation, risk score, and app sensitivity to decide whether access should be allowed.

Centralized governance

Keep identities and entitlements visible across apps so reviews, approvals, and audits are consistent.

Privileged access management

🗝️

Vaulting

Store privileged credentials in a controlled vault instead of spreadsheets or chat.

⏱️

JIT elevation

Grant elevated rights only for a limited time window and only after approval.

🎥

Session recording

Capture privileged sessions to deter misuse and support investigations.

Real-world example: rather than sharing the Linux root password, an admin requests access through PAM, receives a temporary session, and every command is recorded.

Zero trust and IAM

Principle

Never trust by network location alone. Verify user, device, context, and requested resource every time.

Identity role

Zero trust relies on strong authentication, least privilege, and continuous access checks. A widely cited example is Google BeyondCorp, which moved access control from the network perimeter to users and devices.

Step-up MFA for risky logins.

No always-on VPN trust assumption.

Protect service accounts too, not just humans.

IAM attack scenarios

Scenario 1: orphan account

An employee leaves, but the VPN and SaaS accounts remain active. An attacker reuses the credentials and accesses internal tools.

Scenario 2: privilege creep

A developer changes teams multiple times and accumulates rights across old systems, creating hidden risk.

Scenario 3: shared admin account

Nobody can prove who performed a dangerous action because all admins used the same credential.

Scenario 4: MFA bypass attempt

A phishing page steals a password and the attacker pushes repeated OTP requests hoping the user clicks approve.

Quick recap for learners

Identity is the new perimeter.

Authentication proves who the subject is; authorization defines what the subject can do.

Least privilege, MFA, access reviews, and PAM are the most repeated controls because they reduce real attack paths.

Good IAM is not only technology; it is policy, lifecycle discipline, and evidence.

Speaker notes · Session 1

Flow

Start with why identity matters more than perimeter. Use daily examples: office Wi‑Fi, GitHub, VPN, banking app, and company HR portal. Revisit authentication versus authorization several times and ask learners to classify examples aloud.

Instructor emphasis

Keep terminology simple. Ask engineers to list all identities they know: human, admin, service account, bot, API key, workload, and device. Close with a mini whiteboard exercise mapping login flow to policy decision.

Suggested pacing: 45 min concepts, 45 min examples, 30 min discussion, 20 min break, 60 min workshop, 20 min recap and quiz.

Speaker notes · Session 2

Flow

Teach RBAC first because it is intuitive. Then show where RBAC breaks, such as contractor access, geography-specific access, and temporary projects, and introduce ABAC and JIT elevation.

Instructor emphasis

Use a sample company org chart. Ask students to design 5 roles and then identify where separation of duties conflicts would appear, such as requester and approver being the same person.

Suggested board activity: create one bad role model and one improved role model, then compare maintenance effort and risk.

Speaker notes · Session 3

Flow

Demonstrate SSO and federation visually: identity provider, service provider, token, assertion, redirect. Explain why user convenience and central control both improve when SSO is implemented well.

Instructor emphasis

Spend time on phishing-resistant MFA, push fatigue, and conditional access. Connect cloud IAM to real engineering work like AWS roles, Azure RBAC, and workload identities.

Suggested demo: compare a legacy app with local login against a federated SaaS app with SSO and MFA.

Speaker notes · Session 4

Flow

Introduce IGA using business language first: who should have what, who approved it, and how we prove it. Then show how joiner mover leaver, certifications, policies, and audit reports solve that problem.

Instructor emphasis

This is where you add Saviynt and SailPoint. Explain connectors, source systems, authoritative HR data, birthright access, approval workflows, certifications, SoD checks, and remediation tickets.

Suggested activity: give students a fake access review sheet and ask which access should be revoked, retained, or escalated.

Speaker notes · Session 5

Flow

Bring together PAM, zero trust, and attack scenarios. Use incidents and stories rather than only architecture. Engineers remember failure modes better than definitions.

Instructor emphasis

End with practical takeaways: remove standing privilege, protect service accounts, rotate secrets, monitor admin sessions, and make reviews operational rather than annual paperwork.

Final hour idea: team-based case study where each group recommends controls for a breach caused by poor IAM hygiene.

Troubleshooting appendix

Goal

Help engineers think systematically when access, provisioning, certification, or connector processes fail.

Approach

Validate source data, identity creation, role assignment, workflow state, provisioning logs, and target-system response before escalating.

Teaching note: most IAM issues are not random; they usually break at handoff points between HR, IGA, workflow, connector, and target application.

Scenario 1 · New joiner gets no access

Likely causes

HR record did not aggregate, identity was not created, joiner rule did not fire, role criteria did not match, or provisioning failed at connector or target level.

Check sequence

1. Verify HR source data, 2. confirm identity exists, 3. inspect role assignment, 4. review workflow/provisioning plan, 5. inspect logs and target response.

Classroom line: if access is missing, do not start with the app; start upstream with authoritative source and identity creation.

Scenario 2 · Request stuck in workflow

Symptoms

Request stays pending, no approval mail arrives, no provisioning task launches.

Likely causes

Dynamic approver rules failed, delegated approver data is wrong, workflow logic is incomplete, or notification jobs are not running.

Checks

Validate approver mapping, workflow transitions, mail/job scheduler health, and whether mandatory fields like start or end dates were supplied.

Scenario 3 · Entitlement not visible

Typical reasons

Entitlement is inactive, missing status metadata, not imported correctly, hidden by requestability settings, or not mapped to the right endpoint/application.

What to inspect

Check aggregation results, entitlement status columns, requestable flags, endpoint mapping, and whether the object was filtered out by policy.

Use this to explain why “the app team says the group exists” is not enough; governance metadata must also be correct.

Scenario 4 · Aggregation fails

Connector layer

Bad credentials, expired secrets, network path issues, certificate trust problems, or wrong endpoint URL.

Data layer

Unexpected schema, missing group endpoint, malformed attributes, or target API limits.

Action

Run test connection, read activity logs, isolate source object type, and retry with a narrow scope before full aggregation.

Scenario 5 · Certification data looks wrong

Symptoms

Reviewers see outdated access, missing entitlements, or empty campaigns, and decisions cannot be trusted.

Fix path

Refresh extraction or aggregation first, verify campaign population logic, confirm identities and entitlements loaded successfully, then relaunch or repopulate if needed.

Teaching tip: explain that a certification campaign is only as good as the last successful import of identity and entitlement data.

Scenario 6 · Orphan accounts found

Why it happens

Terminations do not flow downstream, source matching breaks, linked accounts remain after app-side changes, or reconciliation has not run recently.

Response

Confirm source-to-target correlation rules, run reconciliation, check missing manager or HR attributes, disable risky accounts fast, and trace the offboarding event chain.

Key lesson: orphaned accounts are a lifecycle failure, not just an audit finding.

Troubleshooting checklist

Always verify

Source data, identity status, role assignment, workflow state, provisioning plan, connector health, target response, and audit logs.

Avoid

Guessing, directly changing production access without evidence, skipping upstream checks, and treating symptoms before understanding where the flow actually failed.

Best classroom close: “In IAM, troubleshoot in order — source, identity, policy, workflow, connector, target.”
