How SSO works

Single sign-on works through a trust relationship between an identity provider and an application, so the user authenticates once and the application accepts the signed identity response or token instead of asking for a separate password. In common SAML and OIDC flows, the application redirects the user to the identity provider, the identity provider authenticates the user, and then sends the browser back with a signed assertion or ID token that the application validates before creating a session. What happens

The user starts from the application, which is why this is called SP-initiated SSO. The application sees that there is no valid local session and starts federation instead of showing a standalone login page. [web:49][web:55]

Key terms

Service Provider, Browser, Protected Resource.

Why it matters

The application delegates authentication to the identity provider so users can sign in once and reuse that trust across multiple apps. [web:50][web:54]
